# S3 → Cloud Storage

**Moves by:** Storage Transfer Service (STS), repeatable incremental sync.
**Cutover class:** repeatable incremental — STS re-runs move only what
changed, so the source can stay live while it catches up and the final pass
after writes stop is short. Not continuous: there is still a pass to run with
the writers stopped, and it is what makes the copy consistent.

Every command below is yours to run, with your own credentials.

## Substitutions

| Placeholder | What it is |
|---|---|
| `<TARGET_ARGS>` | The targeting arguments exactly as the tool printed them — `address="…"`, plus `directory=`/`identifier=` when it showed them. Two root modules can declare one address, and the bare address is then refused |
| `<SOURCE_BUCKET>` | The S3 bucket name |
| `<TARGET_BUCKET>` | The Cloud Storage bucket the landing zone created |
| `<GCP_PROJECT>` | The project holding `<TARGET_BUCKET>` |
| `<AWS_CREDS_FILE>` | Local JSON file with the read-only AWS key STS uses |

## 1. Prepare the source

- A read-only AWS principal for the transfer: `s3:GetObject`,
  `s3:ListBucket`, and `s3:GetObjectVersion` if versions matter.
- Decide whether object **versions** are in scope. STS moves current versions;
  version history is a separate decision and usually a separate, one-off copy.
- Note the lifecycle rules and the storage classes in use. Neither transfers —
  both are re-expressed on the target in step 2.

## 2. Prepare the target

The landing zone Terraform has to be applied first: `<TARGET_BUCKET>` is one
of the resources it creates.

Before the first sync, settle three things that are cheap now and expensive
after 12 million objects have landed:

- **Location.** Regional in the GKE cluster's region unless access is genuinely
  multi-region. Multi-region costs more and is not a latency win for a
  single-region workload.
- **Uniform bucket-level access.** S3 object ACLs have no equivalent; Cloud
  Storage uses IAM. If the application relies on per-object ACLs, that is an
  application change, and it is better found now.
- **Lifecycle rules**, re-expressed. Storage class names differ (`STANDARD_IA`
  is `NEARLINE`, `GLACIER` is `ARCHIVE`, roughly), and the retrieval semantics
  differ with them.

## 3. Run the copy

```bash
gcloud transfer jobs create s3://<SOURCE_BUCKET> gs://<TARGET_BUCKET> \
    --project=<GCP_PROJECT> \
    --source-creds-file=<AWS_CREDS_FILE> \
    --schedule-repeats-every=1h
```

Let it run on the schedule while the source is still serving. Watch the first
pass to completion before assuming the schedule is enough — the initial copy is
the one that hits bandwidth limits.

**Egress.** This is a cross-cloud bulk transfer and AWS charges for it. Egress
during co-existence routinely runs several times the unbudgeted estimate;
price the whole object set before starting, not after the first invoice.

## 4. Validation gates

- Object counts match between source and target.
- A hash sample matches. STS compares checksums itself, so the sample is a
  spot check rather than the primary control.
- Lifecycle rules are active on the target and do what the S3 ones did.
- The application can read a signed URL from the target — see limitations.

## 5. Cutover

1. Stop the writers, or switch them to write to both.
2. Run one final transfer pass and let it finish.
3. Repoint the application at `gs://<TARGET_BUCKET>`.
4. Keep the S3 bucket readable but not writable.

## 6. After cutover

After the soak, retire the transfer job, then the bucket, then report:

```
mark_data_service_migrated(<TARGET_ARGS>, target="gs://<TARGET_BUCKET>")
```

## Rollback

Repoint the application at S3. It is still readable and its contents are
current up to the final pass; objects written to Cloud Storage after cutover
are not there, so the rollback window is exactly as long as you can tolerate
losing new objects.

## Known limitations

- **S3 signed URLs do not work against Cloud Storage.** The signing algorithm
  differs. If the application hands out signed URLs, that code changes at
  cutover — this is the single most common surprise in an S3 move.
- Object ACLs do not translate. IAM, and optionally uniform bucket-level
  access, replace them.
- Storage classes are named differently and their retrieval behaviour differs.
- Lifecycle rules are re-expressed, not copied.
- Object metadata survives; S3-specific features (object lock, requester pays,
  event notifications) need their GCP counterparts wired separately.
- Event-driven transfer from S3 exists and is worth using for a live bucket
  with a long tail of writes, but it needs the S3 event configuration in
  place first.
